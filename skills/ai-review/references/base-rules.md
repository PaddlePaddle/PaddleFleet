# PaddleFleet 基础评审规则

本文件是每次 PaddleFleet 评审都必须加载的基础规则。

## 评审判定原则

本节约束如何应用下列各节的检查项：先建立证据，按真实影响判定，避免把模式本身当作缺陷或强行套用清单。具体优先级、评论格式和发布策略由调用方决定，本节只约束判定依据。

- **按真实影响判定，不因模式升级问题**：设计味道、缺类型注解、函数偏长、`isinstance` 分派或个人偏好本身不构成问题；只有能指出可达失败或具体维护成本时才报告。判定依据必须是已证实的影响，而不是"这种写法在别处可能出问题"。
- **设计原则是上下文默认值**：代码与需求支持等价合理的替代方案时应接受，不得仅为满足清单而要求新增抽象、回退、缓存、拆分函数或补测试。函数长度本身不是拆分理由，只有职责混杂、输入输出不清或依赖使改动难以推理时才建议按职责拆分；封闭类型集合上的显式分派可能比多态更清晰。
- **只处理现实中的失败**：外部输入在边界处校验，真实 I/O、通信组和 worker 失败的超时、重试、清理要保留；但不要为内部契约已排除的状态加回退，也不要用把非法内部状态伪装成正常结果的默认值。已在可信边界确立的契约不必在每个下游函数重复断言。
- **每个事实只有一个权威来源**：独立存储又各自更新、更新或失效路径不一致的派生值应报告；但明确了 owner、生命周期和一致性契约的缓存或快照不算重复。
- **重构围绕真实概念**：已经开始分叉的重复策略分支、打补丁的兼容层、为假想需求预建的通用框架应报告；重构限定在本次变更范围内，第二次使用或重复计数本身不构成引入抽象的理由。
- **只评本次变更引入或恶化的问题**：把相关的存量问题与本 PR 结论分开，不做无关清理，不重复报告 CI 已强制的格式问题。
- **评判提交物本身，不揣测作者**：不从代码风格、行文或提交量推断是否 AI 生成、作者是否理解或是否用心；对人类与 coding agent 提交的代码适用同一套规则。

## 功能正确性与兼容性

- 核对 PR 描述与实现是否一致，包括配置值、后端、支持的 shape/dtype 和测试范围。
- 检查空输入、零值、负值、上下限、重复输入、非法格式和异常路径，避免只覆盖正常流程。
- 公共 API、配置项、默认值、state dict 或序列化格式变化必须保持向后兼容，或提供明确迁移方案。
- 修改 `TransformerConfig`、`ModelParallelConfig` 时，同步检查 CLI/YAML 入口、默认值、所有消费方和配置测试。
- 跨模块变更必须检查接口两端，避免签名、返回值、dtype、shape、设备或生命周期约定不一致。

## 分布式训练

- 修改 `parallel_state.py`、`process_groups_config.py` 或通信逻辑时，检查进程组创建顺序、rank 成员、销毁和重新初始化。
- 集合通信必须使用正确的通信组，并保证各 rank 的调用次数、顺序、tensor shape 和 dtype 对称。
- 检查 TP、PP、EP、CP 组合下的局部 shape、序列切分、位置编码、随机数同步、共享权重和流水线边界。
- MoE 路径重点检查 top-k/归一化、token dispatch/combine 顺序、expert index、容量与丢弃策略、共享专家及梯度对称性。
- 重计算和 CUDA Graph 变更必须保持前向/反向一致、随机状态正确、地址稳定，并为动态 shape 保留安全回退路径。

## 算子、数值与性能

- 新增或修改 C++/CUDA 算子时，同步检查构建源文件、注册名、Python 封装、签名、版本要求和测试。
- 检查 shape/dtype 推导、设备与 stream、整数宽度、索引边界、内存生命周期和 kernel launch 错误处理。
- FP8、融合算子、Triton、TileLang 和 cuDNN 路径必须有明确的硬件/shape/dtype 保护，并与非融合实现保持数值一致或提供回退。
- 关注热路径中的主机同步和多余拷贝，如 `.cpu()`、`.numpy()`、不必要的 `to_tensor` 或 `contiguous()`。
- 检查低效循环、重复计算、内存泄漏及资源未释放；性能建议必须说明实际热点或复杂度影响。
- 处理除零、`log(0)`、空 mask 等情况时先判定它是受支持输入、非法输入还是被破坏的不变量，再决定拒绝输入、让不变量显式失败还是采用保持算法语义的数值处理；不要反射式地加 `eps`/`clamp` 掩盖脏数据或改变估计量。
- `packages/paddlefleet_ops/third_party/` 属于第三方代码，修改时应说明上游来源、修改原因和后续同步方式。

## 安全与错误处理

- 禁止硬编码密钥、令牌和凭据；外部输入必须经过校验，不能直接拼接到 shell、路径或反序列化操作。
- 检查权限、认证和敏感数据处理是否符合最小权限原则。
- 不使用 Python `assert` 承担运行时输入校验；应抛出明确异常并保留有效错误信息。
- 避免无处理的宽泛 `except Exception`，确认文件、显存、通信组和临时资源在失败路径中正确释放。

## 代码质量

- 函数职责应清晰，命名应表达真实语义；仅在影响理解、复用或正确性时提出可读性问题。
- 删除、重命名或移动代码时，检查导出、注册、调用点、文档和兼容别名是否同步。
- 新文件应包含仓库要求的版权声明；依赖和 lockfile 变更必须与实际需求一致。

## 测试质量

测试细则见[单测规则](unit-test-rules.md)：仓库模块主表、各模块的无卡/单卡/多卡适用范围与证据要求、用例设计与运行方式，反例见[典型单测反例](unit-test-antipatterns.md)。评审测试时按该文件判定。

- 修改 `ci/rules` 时同步检查 `ci/rule-tests` 和快照；新增 blacklist 不能替代回归测试。

## PR 信息与评论

- 检查 PR 标题是否清晰概括修改对象和目的；类别前缀可参考 PaddleFleet 仓库惯例，不强制单一格式。
- PR 描述必须按仓库模板填写并去掉占位注释：`### PR Category`、`### PR Types`、`### Description` 三段非空（`Require PR Description` 门禁 `ci/checkPRTemplate.py` 会据此拦截），`### 是否引起精度变化` 明确填"是/否"。`PR Category`、`PR Types` 只能取模板列出的枚举值，取值不在枚举内会判 FAILURE；描述缺段或留占位注释时，先提醒补全再展开评审。
- PR 描述至少说明为什么修改、解决什么问题，以及必要的验证方式；描述与实现不一致时指出具体差异。bug 修复要给出复现或回归测试，特性或重构要给出验收标准或需保持的行为；缺少这些证据时按"哪项行为未被验证"提出，而不是替作者假设已验证。
- 改默认值、数值路径、算子实现或并行策略时，`### 是否引起精度变化` 的结论必须与实现一致；填"是"要说明影响范围与验证方式（与[用户配置开关规则](user-configuration-rules.md)对默认值变更的要求一致）。
- 评论必须具体、可执行并解释影响原因；意图不明确时先提出精确问题，不给出空泛总结。

## 跟进评审

- 每个语义问题只保留一个讨论线程，区分已解决、部分解决、未解决和被取代；行号变动时复用原线程，不新开重复讨论。
- 不重复报告未变代码上的相同问题，也不在每一轮为未改动代码新增可选优化；已达成一致的问题只有出现新证据才重开。
- 复核修正时把改动与原始问题及其验证对照：新的 commit 或一句"已修复"不等于问题已解决；作者用代码证据推翻某条问题时，接受合理的反对意见。
